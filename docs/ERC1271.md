# ERC-1271, Safes and off-chain signatures for the agent

## Why the agent has no general ERC-1271

Kernel routes `isValidSignature(hash, sig)` for a permission through
`policy.checkSignaturePolicy(id, caller, hash, sig)`. A policy sees the
*caller* (the contract asking) and a 32-byte hash — never the typed data
behind it. An agent that may produce valid 1271 signatures can therefore
sign an ERC-2612 permit, a Permit2 transfer, a USDC
`transferWithAuthorization`, or a DEX order, and the funds move without any
call ever passing the allow-list. `AgentPolicy.checkSignaturePolicy` therefore
refuses every hash — except one kind it can check in advance: an x402 payment
the agent registered first, within the mandate (below).

What stays refused, by design: Permit2 flows, SIWE logins as the account,
ERC-8128 HTTP auth, ERC-8004 wallet binding by signature, Safe `v = 0`
contract signatures.

## x402 — registered authorizations (implemented, AgentPolicy v6)

x402 `exact` on EVM pays with an EIP-3009 `transferWithAuthorization`: the
payer signs it, the server's facilitator submits it. For a smart account the
facilitator (and USDC itself, at settlement) checks the signature with
ERC-1271 — where the policy sees only a hash. The way around: the agent first
tells the policy *what* it is about to sign, in an ordinary operation that
the mandate judges.

1. **Register.** An agent operation calls
   `AgentPolicy.x402Authorize(token, from, to, value, validAfter, validBefore, nonce)`.
   Validation decodes it like any other call: `from` must be the account,
   the token must have a limit with its EIP-712 domain (`"x402": true` in
   the config), `value` must fit `maxPerOp` and the remaining token budget
   — **the same budget transfers use**. It books `value` as spent and
   records the authorization's digest. The call itself only emits
   `X402Authorized`.
2. **Sign.** The agent key signs the digest, Kernel-wrapped
   (`Kernel(bytes32 hash)` in the account's domain), as a permission
   signature `0x02 ‖ permissionId ‖ 0xff ‖ r ‖ s`.
3. **Pay.** The request is retried with `PAYMENT-SIGNATURE`.
   `checkSignaturePolicy` vouches for exactly the registered digests, until
   `min(validBefore, validUntil)` and not before the window's `validAfter`;
   anything else is refused as before. It does not check the caller — the
   facilitator verifies through `eth_call` — and needs not: a registered
   authorization can move only what was booked, to whom it names, once
   (USDC burns the nonce).

An authorization that expires unused leaves its amount booked; the agent
returns it with `x402Reclaim(...)` (also an allow-listed call), which the
policy accepts only past `validBefore` and only if the token reports the
nonce unused.

**Revoking the permission cancels every pending payment at once.** USDC
settles a smart account's authorization only by asking the account
(`isValidSignature`) at the moment of settlement, and the account asks the
policy. Uninstalling the permission sets its `validUntil` to 0 and moves it
to a new *epoch*; the registrations live under the old epoch. From that
block on the policy vouches for none of them, so even an authorization the
agent already signed — held by a facilitator, a server, or an attacker —
reverts at the token: nothing more can leave under that permission.
Reinstalling the same permission id starts a new epoch with no
registrations and a fresh budget; old authorizations stay dead. (Test:
`test_x402_revokeKillsSignedAuthorizationsAndReinstallStartsClean`; an
independent re-audit on 2026-10-21 confirmed it.) Reclaiming expired
registrations before a planned rotation is therefore budget bookkeeping
only, not a safety step.

The config side (`signer/agent.x402.base-sepolia.json`):

```json
"allow": [
  { "target": "<agentPolicy>", "selector": "0x4993d616" },
  { "target": "<agentPolicy>", "selector": "0xf3ea183e" }
],
"tokens": [
  { "token": "0x036CbD53842c5426634e7929541eC2318f3dCF7e", "maxPerOp": "100000", "budget": "1000000", "x402": true }
]
```

and the agent side:

```sh
agent-signer x402 fetch --agent agent.x402.base-sepolia.json --env-file .env http://localhost:4021/quote
agent-signer x402 reclaim --agent agent.x402.base-sepolia.json --env-file .env
```

`x402 fetch` takes the `exact` offer on this chain in a token the mandate
pays x402 in, registers it (lifetime: the server's `maxTimeoutSeconds`, at
least 120 s), signs, checks `isValidSignature` on the account itself, then
pays. `--max-amount` adds a local cap. A demo server is in
[`examples/x402`](../examples/x402/README.md).

Verified on Base Sepolia (2026-10-21) against the public x402.org
facilitator (`@x402/evm` 2.28): the bundler accepts the registering
operation (it writes the policy's storage for the account during
validation, like `spent`), and the facilitator's strict ERC-1271 check
passes, and the payment settles: `x402 fetch` got `200` and the
facilitator's settlement tx `0xd3535c28…a31d` moved 0.001 USDC from the
account (agent key in TROPIC01); the ElizaOS example's `PAY_FOR_URL` paid
the same way (tx `0x344e9444…1757`). Before the account held USDC, the
facilitator refused only with `invalid_exact_evm_insufficient_balance`. Two such unsettled registrations were
returned by `x402 reclaim` after they expired (USDC `spent` back to 0).

## Variant 1 — Safe pass-through (implemented)

Olas services and Jinn operators act through a Safe whose owner is the
agent. With the Kernel account as that owner, the agent does not need to
*sign* for the Safe at all: the account calls

```
Safe.execTransaction(to, value, data, operation, safeTxGas, baseGas,
                     gasPrice, gasToken, refundReceiver, signatures)
```

with `signatures = r ‖ s ‖ v` where `r = owner address`, `s = 0`, `v = 1` —
a *pre-validated* signature the Safe accepts because `msg.sender` is that
owner. This is the same `v = 1` path Jinn's daemon already uses
(`buildSafeSignature`).

On its own that would blind the policy: the outer call is just
`(safe, execTransaction)`. `AgentPolicy` v2 (`contracts/src/AgentPolicy.sol`)
therefore treats an allow-list entry `(safe, 0x6a761202)` as "this Safe may
be driven" and judges the **inner** call:

| Check | Why |
|---|---|
| inner `(to, selector)` on the same allow-list | the mandate means the same thing through the Safe as directly |
| inner `value` (+ outer `value`) within the per-op cap and the budget | Safe funds count like account funds |
| `operation == CALL`, or DELEGATECALL into an allow-listed `(MultiSendCallOnly, multiSend)` whose every leg is a CALL passing the allow-list (values summed) | a delegatecall runs arbitrary code *as the Safe*; Jinn settles through such batches |
| `gasPrice == 0` | otherwise the Safe pays a gas refund in `gasToken` to a `refundReceiver` the agent picks — a drain |
| inner selector ≠ `execTransaction` | no nesting |
| the Safe transaction comes as the batch `[SafeNonceAssert.check(safe, n), execTransaction]` | a `v = 1` signature does not commit to the Safe nonce; the assertion makes a replay revert on-chain (audit F4) |
| the Safe's own functions (`addOwnerWithThreshold`, `enableModule`, `setGuard`, …) | refused unless explicitly allow-listed — the owner never should |

Tests: `contracts/test/AgentPermission.t.sol`, `test_safe_*`, against real
Safe v1.4.1 contracts and `MultiSendCallOnly`; each guard was
mutation-checked (removing it makes a test fail).

ERC-20 amounts are metered per token through a Safe exactly as directly
(audit F2) — for `transfer`, `transferFrom`, `approve` and
`increaseAllowance`; any other value-moving selector is gated by the
allow-list but not metered, so allow-list such selectors with care. One allow-list entry admits its call directly, through a Safe
and as a batch leg alike (audit F5) — curate it with that in mind.

Deployed on Base Sepolia: AgentPolicy v4 `0x3f590A5879B5f28466b6DAeF69FfA9777f84b424`
with `SafeNonceAssert` `0xC14AbFF54D40f4DAf665391E0B7079bd53EB8279` (audit
fixes, see `AUDIT-2026-10-20.md`); v3 `0x460fD3bc…9E24`, v2 `0xEA80a8bd…F6C0`
and v1 `0x12854c1C…D1c7` stay recorded for permissions installed with them. Test Safe
v1.3.0 (Olas' version) owned 1/1 by the agent account:
`0xd0b972a8ee7D8AB91a2e3381Eb6F10550B80E52A`. With the TROPIC01 agent key
under v2 (permission `trs1`, rotation tx `0x8e900b99…21a875`): a call through
the Safe executed (tx `0xf07cbb35…baedf0557`), `addOwnerWithThreshold`
through the Safe was refused at validation (`PolicyFailed`). Then under v3
(permission `trs3`, rotation tx `0xef321bd0…5ff4aa`, mandate adds
`(MultiSendCallOnly 0x40A2…130D, multiSend)`): a two-leg batch through the
Safe executed (tx `0xd9bdc92a…c0fd31`), the owner change is still refused —
`examples/jinn`.

## Variant 2 — caller-scoped ERC-1271 (documented, not built)

When the Safe is driven by a relayer or has several owners, owners sign the
Safe transaction hash off-chain and the Safe verifies a contract owner with
`isValidSignature` (`v = 0`). Kernel then calls
`checkSignaturePolicy(id, caller = the Safe, hash, sig)`.

Design:

- `AgentPolicy` keeps, per `(account, id, epoch)`, a set of **allowed
  1271 callers**, installed with the mandate and changed only by the owner
  (root) key — e.g. exactly the service Safe.
- `checkSignaturePolicy` returns success only if `caller` is in that set;
  tokens, Permit2, DEX settlement contracts are never in it.
- Consequence to accept explicitly: the agent can then approve *any*
  transaction of that Safe; its limits must move into the Safe — a Safe
  Guard (`checkTransaction`) enforcing the same allow-list/cap, or Zodiac
  Roles. Without a guard, variant 2 hands the agent the Safe's whole balance.
- Kernel wraps the hash in its own EIP-712 domain before the signer sees it;
  `agent-signer` must sign that replay-safe digest, not the raw Safe hash.

## Off-chain authentication (SIWE, ERC-8128, announcements)

These are verified by services via `eth_call`, where `caller` is arbitrary,
so caller scoping cannot help. The safe pattern is a **separate identity
key** with no funds and no permission on the account — another hardware
key, or the agent's TEE/OS key — published once (for example in the ERC-8004
registration) and used for authentication only. Losing it leaks identity,
never money.
