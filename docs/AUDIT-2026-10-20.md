# Security audit — 2026-10-20

## Scope and method

- **Revision:** `2428911` (`master`), everything committed on 2026-10-20 —
  Phases 0–3.5: the Rust signer workspace (`hw-signer` backends, the
  `agent-signer` CLI) and the Foundry contracts (`P256Validator`,
  `P256Signer`, `AgentPolicy` v1–v3, `WhitelistPaymaster`).
- **Auditor:** a separate Claude session (`security-audit-playbook-13`),
  verifying each mechanism firsthand at the ref rather than from summaries.
  Secrets (`.env`, the gas-wallet key) were out of scope and not read.
- **Depth:** the on-chain authorization bound was judged as value-bearing;
  everything else at testnet depth (current exposure: Base Sepolia only, no
  real funds). Hardware/chain behaviour was accepted as evidence from the
  developer's runs; the auditor did not drive a TPM or a live chain.

### Security model under review

- The agent's P-256 private key never exists outside the secure element.
- The chip signs any digest the host asks for; the **host is untrusted**.
  The only authorization boundary is on-chain: `AgentPolicy` bounds what the
  agent permission can execute; only the owner (root) key can change or
  revoke it.
- Question audited: can a fully compromised host, holding the agent
  permission's signing oracle, execute anything beyond the mandate or reach
  the root path?

### F8 — Owner (root) key reachable from the agent host (governing)

- `signer/crates/agent-signer/src/chain.rs:90-92` opens the **owner** signer
  unconditionally in every session, before the pinned-account branch — even
  for an agent operation on a deployed account, where nothing derived from
  the owner key is used. `chain.rs:361` signs root operations with
  `cfg.owner` in the same binary: the agent runtime is wired to hold
  owner-signing capability.
- `signer/crates/hw-signer/src/tpm.rs:80-82, 89-94`: unsealed keys get
  `userWithAuth` with an empty authValue, used through an empty password
  session. In the live deployment the owner key (`0x81010010`) and the agent
  keys sit in the same TPM, so any local process with `/dev/tpmrm0` access
  (group `tss`) can sign a root UserOperation — uninstall or rotate the
  agent permission, execute anything.
- Ruling: one architectural defect — owner/agent separation is enforced
  neither by the code nor by the default deployment, and it survives "just
  use a TPM". It governs F1.
- Fix lanes:
  - **code** — the agent path never opens the owner key; with a pinned
    account nothing is derived from it; root operations are refused when the
    owner key has no authorization, unless an explicit testnet flag is set;
  - **custody (owner's decision)** — the owner key off the agent host, on a
    separate device, with authorization.
- Severity: low on testnet today (no funds); for value-bearing use, a
  custody prerequisite.
- **Owner's position (agreed after discussion).** The project's key policy
  ([`KEY_POLICY.md`](KEY_POLICY.md)) assumes an attacker running user-level
  code on the agent host is indistinguishable from the agent, and that
  per-process access control to the chip cannot be relied on. Under it:
  - an authValue on the owner's TPM key on the same host protects nothing,
    so that fix is dropped, and so is "refuse root operations without
    authorization";
  - the owner key must not live on the agent host at all (policy rule 3);
    co-locating both keys in one TPM is a knowing testnet-only exception
    (rule 6), not a code defect;
  - the real code defect is that the agent's operations **require** the
    owner key: `agent-signer` opens it in every session, which makes moving
    it to another device impossible. Fix: the agent path never opens the
    owner key.

### F1 — Software key reachable for chain-sending commands

- `agent.rs:57` `KeySpec::Software` accepts a hex scalar from the config for
  **both** `owner` and `agent` (`agent.rs:84-85`); `open_signer`
  (`agent.rs:215-217`) only prints a warning. `op send` → `send_op` →
  `open_signer` reaches it. `hw-signer` has `default = ["software"]` and
  `agent-signer` depends on it, so it is in every build.
- A software owner key is the root in plaintext: full takeover.
- Fix: behind an explicit non-default feature, refused for every
  chain-sending command, and unconditionally refused for the owner slot.

### F2 — Token amounts unmetered

- `AgentPolicy.checkUserOpPolicy` and `_judge` meter only native value; for
  calldata they check `(target, selector)` only. An allow-listed
  `(token, transfer)` moves any amount; one allow-listed `(token, approve)`
  grants an unlimited allowance that is then drained outside the budget.
- Fix: decode and cap `transfer` / `transferFrom` / `approve` amounts per
  token (per operation and cumulatively).

### F3 — Gas outside the budget; shared paymaster without caps

- `WhitelistPaymaster._validatePaymasterUserOp` sponsors any listed sender
  with no per-account or per-operation limit and no `postOp` accounting: one
  compromised sponsored account can drain the shared deposit for all.
- Unsponsored, a compromised host can burn the account's own EntryPoint
  deposit through fees; reverting operations still pay.
- Fix: per-account gas budget and per-operation cap in the paymaster
  (`postOp` refunds the unused part), and gas counted in `AgentPolicy`'s
  budget when the account pays.

### F4 — Double execution through a Safe

- A pre-validated (`v = 1`) Safe signature from `msg.sender == owner` does
  not commit to the Safe nonce, so two distinct UserOperations carrying the
  same `execTransaction` both execute. The only guard (`--nonce` pinning in
  `chain.rs`) lives in the untrusted host layer.
- Teeth: an honest retry can fire twice; compounds F2.
- Fix: an on-chain Safe-nonce assertion bound to each Safe transaction.

### F5 — Shared allow-list across contexts

- One `(target, selector)` entry is usable directly from the account,
  through a Safe and as a MultiSend leg. Not a vulnerability; the mandate
  documentation must say so.

### F6 — Short calldata treated as a value transfer

- `AgentPolicy._selector` maps 1–3 bytes of calldata to selector
  `0x00000000` (plain transfer), but the EVM runs it as the target's
  fallback. Allow-listing `(target, 0x00000000)` therefore also admits
  fallback calls with short data.
- Fix: refuse 1–3 byte calldata.

### F7 — No on-curve check at install

- `P256Validator.onInstall` and `P256Signer.onInstall` reject only `x == 0`
  or `y == 0`. An off-curve key fails closed (the account bricks itself) —
  a footgun, not a bypass.
- Fix: check the point is on P-256 at install.

## Verified clean

- The policy's calldata parsing matches what the targets execute: Kernel
  `execute` (same `ExecLib.decodeSingle`), `Safe.execTransaction` under Safe
  v1.3.0's ABI coder v1 (`to` as the low 160 bits, `operation` and
  `gasPrice` required to be zero words), MultiSendCallOnly legs (operation
  byte enforced per leg); no nesting or recursion.
- `userOpHash` binds chain id, EntryPoint and nonce; keys are scoped per
  `(permission id, account)`; an agent operation cannot ride the root path.
- Every backend normalizes to low-s and Solady rejects high-s.
- The permission epoch invalidates stale allow-list entries on uninstall.
- Value is charged conservatively at validation.

## Resolution

Fixed in code on 2026-10-20 (contracts: `AgentPolicy` v4, `SafeNonceAssert`,
`WhitelistPaymaster` v2, `P256Point`; signer: `agent-signer`, `hw-signer`).
Every new guard was mutation-checked: removing it makes a test fail.
Deployment to Base Sepolia and the agent's rotation onto the new modules are
separate, owner-approved steps, recorded below when done.

| # | Fix | Tests |
|---|---|---|
| F8 (code) | `agent-signer` never opens the owner key for the agent's operations: the session takes the owner's *public* key from the config (`ownerPublicKey`) and fails closed when the account is neither pinned nor derivable; the owner key is opened only to sign a root operation. A TPM owner key can share the chip behind the root/user boundary: `key create --auth-file`, the key **created** with an authValue (SHA-256 of a root-only file), `{"tpm": {"handle", "authFile"}}` in the config. Custody placement is the owner's (`KEY_POLICY.md` rule 3). Shown live: an agent session ran with no access to the TPM that holds the owner key. | `agent_session_never_opens_the_owner_key`; hardware `protected_key_signs_only_with_its_auth` (the TPM refuses a wrong and an empty authValue; a key created without auth fails it) |
| F1 | `KeySpec::Software` is refused in every role (owner, recovery, agent) unless built with `--features insecure-software-keys` — a test-only feature, never in a release. (At the audit the feature admitted only the agent; since `1d91818` it admits every role so the end-to-end tests can sign owner and recovery operations — re-checked by the auditor on 2026-10-22.) | `software_keys_are_refused` (all three roles, with and without the feature) |
| F2 | `transfer` / `transferFrom` / `approve` / `increaseAllowance` amounts are capped per operation and by a per-token budget (`policy.tokens` in the config); an allow-listed token selector without a limit is refused, even for a zero amount. | `test_token_*` |
| F3 | `AgentPolicy` counts the maximum gas cost against the budget when the account pays for itself. `WhitelistPaymaster` v2 gives each account a gas budget and a per-operation cap, charged at the operation's maximum cost at validation (no `postOp`, so no stake needed); `paymaster sponsor --budget --max-per-op`. | `test_gas_selfPaidCountsAgainstBudget`, `test_perOperationCapHolds`, `test_budgetRunsOut` |
| F4 | A Safe transaction is admitted only as a Kernel batch `[SafeNonceAssert.check(safe, n), safe.execTransaction(...)]`; a replay reverts on-chain. `op send --safe-nonce n` builds it; the Jinn and Olas examples pass the nonce their Safe transaction was meant for. | F6 | 1–3 bytes of calldata are refused. | `test_shortCalldataIsRefused` |
| F7 | `P256Validator` and `P256Signer` check the key is on P-256 at install (`P256Point`). | `test_offCurveKeyIsRejected` |
